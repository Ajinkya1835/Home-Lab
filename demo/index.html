One box. Fourteen containers. Zero surprises.

A repurposed laptop runs my whole self-hosted stack — photos, media, files, passwords, automation and monitoring — behind Tailscale. The server's configuration is a git repository, so the machine can be rebuilt from the last commit and every deploy is validated before it lands.

The stack

Media & files

Jellyfin for films and shows, Immich (server, ML, Postgres, Redis) for photos, File Browser for the encrypted data disk.

Ops & health

Netdata for metrics, Dozzle for logs, Scrutiny for drive SMART health, a status page, and noVNC for a remote desktop.

Secrets & automation

Vaultwarden holds credentials; n8n runs outreach pipelines and webhook jobs; cron covers backups, snapshots and config sync.

Exposure model

Public

Only explicit Tailscale Funnel endpoints — media streaming, photo sharing, the vault. Nothing else answers from the internet.

Tailnet only

Admin surfaces (logs, metrics, remote desktop, dashboard) are reachable from my devices and nowhere else.

Internal

Databases and the ML worker sit on private bridge networks with no published ports at all.

How a change reaches production

  1. Edit a compose file or a stack's config on the host.
  2. CI resolves every compose file with docker compose config -q, runs shellcheck and gitleaks.
  3. A 5-minute timer pulls the repo, re-validates, and recreates only the stacks whose hash changed.
  4. A failed validation leaves the previous container running and posts one high-priority alert.
# every stack, every push
for d in docker/*/; do
  (cd "$d" && docker compose config -q \
     --no-interpolate) || exit 1
done
shellcheck -S error bin/deploy
gitleaks detect --no-banner

What automation actually does

03:00 — backup

Encrypted snapshot of config and database dumps to the backup disk, with a SMART check on the data drive at the same time.

03:40 — config sync

Live config is copied into the repository, scanned for secret-like content, then committed and pushed. The repo always matches the machine.

every 5 min — deploy

Pull, validate, recreate only what changed. The deploy script is idempotent, so a manual run and a timer run do the same thing.

08:00 — digest

One morning message: what changed overnight, what is red, what needs attention. Failures are deduplicated before they are sent.

Rebuild story

The original boot drive died. Because compose files, host config and the runbook lived in git — and the data disk was LUKS-encrypted and independent — the replacement machine came back with the same services, same ports, same backups. Data loss: none.
